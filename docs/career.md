# 学生求职模式：Agent 应用开发与后端

首版面向计算机相关专业学生的实习与校招，以已有简历优化为主，支持从零经历访谈。沿用 CLI 和 Tk 桌面界面，模型与联网配置继续使用现有 `.env`。

## 启动

```powershell
conda activate agent
python -m pip install -e .
python career_gui.py
```

CLI 使用 `python career.py`。安装后的命令分别是 `career-agent-gui` 和 `career-agent`。原来的 `main.py`、`gui.py` 默认为通用模式；也可通过 `.env` 中 `AGENT_MODE=career` 切换。没有配置真实模型 API Key 时不能进行模型对话。

Windows 在项目目录也可执行 `start_career_gui.cmd` 或 `start_career.cmd`，启动器会明确使用 Conda 的 `agent` 环境，避免误用系统 Python。源码入口会自动添加本项目的 `src`，无需手改为 `src.deepseek_agent` 导入。

诊断环境可执行 `python career_gui.py --check`，或 `start_career_gui.cmd --check`。它只显示解释器、源码位置和依赖状态，不打开窗口或调用模型。PDF 依赖必须安装到实际运行应用的解释器；错误消息会给出对应的完整安装命令。

## 已有简历

1. 将文件放入 `AGENT_WORKSPACE`（默认项目目录），通过桌面“导入简历”选择文件，检查填入的提示后发送；也可直接粘贴文本。支持 UTF-8 TXT、Markdown、DOCX 和可提取文字的 PDF。
2. 使用“简历诊断”，先查看最值得处理的问题；回答职责、技术方法、验证和成果方面的追问。
3. 提供目标 JD，再使用“岗位分析”。系统依据具体要求分析 Agent、后端或复合岗位，并说明证据、缺口及准备建议。
4. 保存经历事实时会出现确认窗口。核对 statement、稳定 key、来源 ID 和 source_quote 后再同意；拒绝不会写入事实。
5. 查看模型展示的逐条原文、建议、理由和事实依据。请求保存为修改报告；新报告始终是草稿。
6. 接受或拒绝报告需要工具确认。请求“把这份报告导出到 review.md”；导出也需要确认，首次创建新的 Markdown 文件；相同报告与路径重试时，核对一致才复用原结果。
7. 使用“项目面试”围绕项目和目标岗位练习；一次一个问题，反馈中的事实需要确认后才加入长期档案。

没有简历时选择“从零整理”，介绍课程设计、项目、竞赛、科研或实践。经访谈确认后，助手使用 `build_resume_draft` 将事实组织为初稿，再进入相同的优化流程。该初稿保留生成依据，不能被工具反向当作新的个人事实来源。

CLI 命令：

| 命令 | 用途 |
| --- | --- |
| `/resume resume.pdf` | 导入工作区相对路径的简历；路径有空格时可加双引号 |
| `/resume` | 多行粘贴简历；单独输入 `/end` 提交，`/cancel` 取消 |
| `/jd` 或 `/jd job.md` | 粘贴或导入 JD |
| `/diagnose` | 简历诊断 |
| `/match` | 对照目标岗位分析 |
| `/interview` | 开始项目面试 |
| `/memory` | 查看确认事实、来源文档与报告索引 |
| `/exports` | 查看当前档案最新 50 条导出记录，不调用模型 |
| `/exports <完整导出 ID>` | 核对记录对应的当前文件，不调用模型或重新导出 |
| `/forget <完整事实 ID>` | 用户确认后删除事实及纠正历史 |

随附虚构样例 `examples/career/student_resume.md` 和 `examples/career/agent_backend_internship.md`。在 CLI 依次执行 `/resume examples/career/student_resume.md`、`/jd examples/career/agent_backend_internship.md`，然后 `/match`。样例不代表真实学生或招聘信息。

## 长期记忆与版本

- 每个档案保存到 `data/career/<档案 ID>/`，包含 `profile.sqlite3`、默认会话、项目分组和运行日志。设置 `AGENT_CAREER_PROFILE_ID=student_01` 可以使用另一个档案。
- 导入材料只是来源；个人事实需要实际工具确认。来源引文必须逐字存在于导入简历或当前用户输入。JD 不能作为个人经历来源。
- 同一事项使用相同 key。相同 key 的分类、陈述、来源 ID 和来源引文完全一致时，重复保存返回原事实，保留 ID、revision、更新时间和修订历史，不使初稿或报告过期。真正修改上述任一字段才增加 revision；每次模型调用注入当前事实，旧对话不应覆盖纠正。
- 重复保存仍需用户确认并重新检查来源；`current_user` 引文必须存在于本轮用户原话，不能凭历史成功保存绕过。比较使用现有字段校验后的值，不做语义相似合并，不跨 key 或档案去重。完整来源和其他事实通过业务工具查询。
- 模型修改草稿独立保存，接受报告不会自动改写个人经历。修改项必须引用当前确认事实，原文必须存在于指定简历。
- 事实纠正或删除后，引用旧 revision 的初稿和报告会失效。旧初稿不能生成新报告，旧报告不能继续接受或导出；先重建初稿，再重新生成和审阅报告。
- `/new` 和清空对话不会删除长期档案。删除事实不会自动删除原始简历、导出文件或聊天历史；原始材料仍可能出现旧描述。完整清理时关闭应用，另行管理该档案目录及已导出的文件。
- 数据目录已被 Git 忽略，并禁止通用文件工具直接访问。求职模式提供业务工具及时间、计划、可选联网工具，不开放命令执行和任意文件修改。

## 首版边界

PDF 依赖 pypdf；DOCX 提取正文段落与表格中的文字。读取上限为 5 MB、20 页 PDF 和 50000 字符，超限时拒绝导入，不悄悄截断。扫描 PDF 和图片没有 OCR，旧版 DOC 应转换为 DOCX。复杂排版提取后需要核对文字顺序；详见 [pypdf 文本提取说明](https://pypdf.readthedocs.io/en/stable/user/extract-text.html)。

导出的是包含诊断、逐条修改、来源和审阅状态的 Markdown 报告，本版不提供排版后的 PDF／Word 简历，也不自动投递。

本地档案 ID 用于隔离数据，不是账号认证。本版适用于本地学生助手；多用户服务还需要独立认证与授权设计。确认后的记忆、简历和对话会发送给已配置的模型服务；仅在用户要求实时岗位搜索时使用联网工具，系统提示禁止向搜索参数传递私人简历内容。

来源校验、用户确认和 revision 检查由代码执行；建议的专业判断与语义准确性仍依赖模型，需要用真实简历与 JD 进行人工验收。不能将事实 ID 存在等同于模型建议已经被语义证明。

## 结构化报告与证据依赖（v2 引入）

`career_review` 的 `save` 操作使用以下格式；`findings` 必须显式提供，没有个人经历分析时传空数组。

```json
{
  "action": "save",
  "resume_id": "已导入简历或有效初稿的 ID",
  "title": "简历修改报告",
  "findings": [
    {"text": "参与后端接口测试", "evidence_fact_ids": ["已确认事实 ID"]}
  ],
  "general_advice": ["建议补充测试范围与验证方法"],
  "changes": []
}
```

- `findings` 保存个人经历、能力等判断，每条必须引用 1–20 个存在的事实；`changes` 保留原有的原文、建议、理由和引用约束。
- `general_advice` 只放一般方法建议和待补问题，导出时明确标为“非已确认的个人经历”。代码不具备判断任意自然语言语义的能力，不能因此保证模型不会在此误放个人经历；仍须人工审阅。
- 最终 Markdown 由系统渲染，不再从模型提供的自由正文生成。旧 Python 调用仍可存档 `markdown`，但报告标记为 `needs_review`，禁止接受或导出；与结构化正文混用会被拒绝。
- 初稿只能由 `build_resume_draft` 生成。事实读取、结构化版本依赖采集和初稿保存共用事务，不能通过导入工具伪造派生初稿。
- 报告的依赖是来源初稿、正文判断和逐条修改依赖的并集。所有来源检查与报告保存共用事务。
- 文档与报告查询、记忆索引提供 `dependency_status`、`stale` 和 `stale_reasons`。原因区分 `fact_updated`、`fact_deleted`、`unverified_dependencies`；更新会携带预期及当前版本。
- `tracked` 仅表示结构化依赖已记录，不代表内容已经人工接受或语义得到证明；用户审阅状态仍使用原来的 `status`。

## v1 数据库升级与恢复

当前数据库版本为 v3；v1 档案先执行本节的证据迁移，再完成后文的导出记录迁移，不需要手工删除数据。升级前使用 SQLite backup API 在同目录创建 `profile.sqlite3.v1-<唯一标识>.bak`，包含 WAL 中已经提交的数据。备份失败则不开始升级；表结构修改和版本号更新在一个事务内完成，失败会整体回滚。备份含个人信息，应按原档案同等保护。

升级保留原始简历、JD、事实、修订历史及报告内容和审阅状态。旧初稿和旧报告的依赖不完整，统一标为 `needs_review`；即使旧报告曾为 `accepted`，也不能继续接受或导出。原始简历/JD 不是派生材料，可以继续使用。请通过当前确认事实重建初稿、通过结构化接口重新生成报告，不从旧正文猜测依赖或自动解除核验状态。

需要恢复升级前的数据时，先关闭全部访问该档案的进程，保留当前数据库及可能存在的 WAL/SHM 文件，再把 `.bak` 复制到一个独立恢复档案目录、命名为 `profile.sqlite3`；不要直接覆盖仍在使用的数据库。旧版本程序可读取这个 v1 副本，新版本程序打开它会再次执行升级。备份只包含升级前的数据，升级后的新写入不会包含在内；恢复后的验证通过之前保留两套文件。

本轮迁移仅通过临时测试数据库验证，没有主动打开或迁移真实档案。

## 求职联网外发控制

求职模式的 `web_search` 和 `read_web_page` 现在每次都需要确认，不使用通用模式的自动调用额度。正常查询应从岗位、城市、技术栈和经验要求构造；本阶段未实现自动放行的岗位条件构造器。通用模式保持现有策略。

确认窗口展示第三方接收服务 Tavily 和本次调用参数：搜索的 `query`、`international_query`，以及网页读取的 `urls`、`question` 等。网页提取也会把 question 作为 query 发送给 Tavily，并可能由该服务访问目标站点。balanced 搜索的一次确认覆盖中英文两个请求；不会自动添加本地简历。参数过长、无法在现有确认界面完整展示时，拒绝执行并要求缩短或分批。

邮箱、中国大陆手机号、18 位证件号形式和常见凭据特征会被阻止，即使用户同意也不能放行；检查覆盖 URL 编码、全角字符及零宽格式字符，发送前再检查一次。错误消息不回显命中的敏感值。不静默脱敏或改写参数，避免用户看到的查询与实际发出的查询含义不同。取消或拒绝时不发送请求。

这不是完整的个人信息识别系统：姓名、私人项目细节、部分境外号码、混淆或编码文本等可能无法由规则识别。因此当前采用逐次人工确认，不能声称“所有个人信息均不会外发”。本地工具轨迹/聊天历史仍可能保存原始工具参数，本次没有实现历史数据清理或全局日志脱敏。

确认由现有 ToolExecutor 执行，适配器的 execute 方法属于受信任内部接口，不能直接暴露给远程用户作为授权接口。模型服务接收对话上下文与搜索服务接收查询是两个边界：本次控制不改变已有模型请求，也不使应用变成完全离线应用。

## 求职离线评测

求职多轮评测入口为 `python -m deepseek_agent.evaluation.career_cli --compare-controls --repeat 2`（源码未安装时先设置 `PYTHONPATH=src`）。内置 14 个合成案例，覆盖 30 轮交互；脚本模型驱动真实 Agent、工具、SQLite 和导出流程，网络使用假的 transport。

每轮分别检查实际业务快照、工具轨迹、确认状态、产物和外发请求。默认结果保存在 `data/evals/career-offline.json`。这衡量业务约束和评分器，不代表真实模型质量。案例协议、负对照、人工评分表及尚未执行的真实模型试点预算见 [求职评测说明](../evals/career/README.md)。


## 事实重复保存的边界

该保护适用于模型重试、重复确认、应用重启后再次提交相同事实。业务层在同一 SQLite 事务内读取当前事实并比较；无变化时不执行写入，因此不会增加进程内数据版本或挤掉历史修订。已有错误增长的版本不会自动回退，已过期的产物也不会被自动恢复为有效。

这是当前状态下的内容幂等，不是通用请求幂等：如果事实已从 A 纠正为 B，再提交 A 会被视为一次新的修改，仍须用户审阅确认。持久请求标识、旧请求重放冲突检测、报告/导出的重试去重和任务中断恢复尚未实现。


## 导出记录与结果核对（数据库 v3）

每次确认导出时，应用先在 SQLite 事务中验证报告证据、渲染本次快照并保存准备记录，事务提交后才写文件。记录包含导出 ID、报告 ID、规范化相对路径、工作区身份摘要、UTF-8 原始字节的 SHA-256/长度、当时的报告审阅状态和事实版本，以及开始/结束时间。记录不复制报告全文或保存供应商错误正文。旧版本导出的文件没有记录，不会通过扫描文件猜测或补造历史。

执行状态 `result` 与当前文件核对结果 `file_status` 分开：

| 执行状态 | 含义 |
| --- | --- |
| `pending` | 写入意图已保存，尚未持久化结束结果；可能还没写文件，也可能写完后进程退出 |
| `succeeded` | 文件适配器返回成功，完成记录已提交；不保证该文件后来没有变化 |
| `unconfirmed` | 写入阶段出现异常，无法确认结果；文件可能已经存在 |

`/exports` 返回最新 50 条记录；`/exports <完整导出 ID>` 只读核对，并显示检查时间、当时记录、当前报告状态与证据过期原因。模型工具使用 `career_review` 的 `exports`（可提供 review_id 筛选）和 `check_export`（提供 export_id）操作；它们不需要写入确认。Tk 保留原有界面，可通过对话要求模型调用这些工具；这条聊天路径仍有正常模型调用，CLI 的 `/exports` 查询无需调用模型。本轮未增加 Tk 报告列表页面。

| 文件核对状态 | 含义 |
| --- | --- |
| `match` | 当前文件原始字节的摘要和长度与准备快照一致 |
| `missing` | 检查时目标文件不存在 |
| `modified` | 当前内容与准备快照不一致，包括换行或 BOM 变化 |
| `unreadable` | 文件过大、不是普通文件、无读取权限或路径不符合工作区规则等，无法安全核对 |
| `workspace_mismatch` | 当前工作区与导出时不同，没有读取该相对路径 |

核对不会修改历史执行状态、报告状态或文件，不会再次调用导出工具。`pending + match` 表示虽然历史完成记录缺失，但当前文件内容与准备快照一致；不自动把 pending 改成 succeeded。`succeeded + missing/modified` 表示曾收到写入成功结果，但当前文件已不存在或内容不同，不能继续声称文件完好。核对只代表检查时刻的结果，不保证随后文件不被修改。

文件一致也不代表报告当前仍有效：事实纠正/删除后，旧文件可以保持 `match`，同时返回 `review_stale=true` 和原因；不会删除旧文件或自动解除报告过期。报告从草稿改为接受/拒绝后，原导出记录仍保留当时的审阅状态。本轮继续允许明确标记的草稿导出，不改变既有确认、来源和过期拦截规则。

准备记录提交失败时不写文件；文件写出但完成记录保存失败时，返回包含导出 ID 的“请先核对”提示。工具记录保留 `result_unknown`，避免将可能已发生的副作用当成普通失败。进程被强制终止时来不及保存结束状态，pending 记录仍可在重启后查询。

上述第一步建立结果追踪与核对；当前已增加下文的安全重试。自动续跑、报告保存去重及通用请求级幂等仍未实现。数据库和文件系统没有跨资源原子事务；并发可能留下多个尝试记录，不能宣称整项导出具备分布式 exactly-once 保证。

### v3 升级与备份

新档案直接创建 v3。首次打开 v2 档案前，在同目录用 SQLite backup API 创建 `profile.sqlite3.v2-<唯一标识>.bak`，包含已提交的 WAL 数据，再在一个事务内新增 exports 表、索引并更新版本号；失败时回滚。v1 档案先备份为 `.v1-*.bak`，在同一个迁移事务内完成原有证据迁移和导出表迁移。旧文档、事实、修订历史、报告及其审阅状态保留；旧证据不完整的报告仍保持待核验。已是 v3 时不重复备份，未来未知版本继续拒绝打开。

需要回退时先关闭应用，保留当前数据库及 WAL/SHM，再把备份复制到独立恢复目录验证，不覆盖仍在使用的数据库。升级后的新导出记录不会存在于升级前备份。备份与导出记录都属于本地个人档案数据，应随档案保护。本轮只验证临时数据库，没有主动打开或升级真实档案。

### 对用户和开发者的影响

用户现在能在程序中断后查回导出 ID 和路径，并判断文件是否与当时内容一致；文件被改动、删除或报告已过期时会明确区分原因。CLI 查询不消耗模型额度，Tk 仍使用现有聊天入口。

开发者可以通过导出 ID 关联报告、准备内容摘要、事实版本、执行状态和当前文件观察，在临时环境复现“意图提交前失败”“文件写出前中断”“文件写出后退出”“完成记录提交失败”等故障。后续安全重试可复用这些证据，但本步不会自动重放操作。


## 报告导出安全重试（第二步）

沿用 `ExportReview(review_id, path)` 和 `export_career_review`，不增加工具或参数，不新增依赖，不改变数据库 v3。用户再次确认相同报告和路径后，依次执行：

1. 按工作区规则规范化目标路径，在当前档案中定向查找该工作区/路径的最新导出记录；此查询不受展示列表 50 条限制。
2. 重新校验当前报告的证据有效性，并比较报告 ID、审阅状态、事实版本、渲染内容摘要及字节数；不能凭历史成功绕过当前检查。
3. 安全读取当前文件，只有当前报告、历史准备快照和现存文件一致时，返回原导出 ID、路径、字节数与状态，并增加 `reused=true`、`file_status=match` 和 `checked_at`。这一分支不写文件、不新增记录、不更新历史完成时间；文件未被重写。
4. 路径无历史记录且文件不存在时按正常首次导出执行，返回 `reused=false`。

| 场景 | 处理 |
| --- | --- |
| 原记录 succeeded，当前报告与文件均一致 | 复用原结果，不重复导出 |
| 原记录 pending/unconfirmed，文件已写出且三方一致 | 可复用已核对的现存文件，历史 result 仍保留原值，不伪造过去的成功记录 |
| 文件已存在但当前档案没有对应记录，即使内容相同 | 报同名冲突，不接管用户文件 |
| 路径已有另一报告记录，或报告状态/内容/事实版本变化 | 拒绝复用，用户确认后可选择新文件名 |
| 文件被修改，即使长度不变 | 根据摘要拒绝复用，不覆盖用户修改 |
| 有历史记录但文件已缺失 | 不自动补写，用户确认后可选新路径导出 |
| 文件无法安全读取、路径越界或敏感、报告证据过期 | 停止并说明原因，不写文件 |
| 用户拒绝本次确认 | 不核对、不复用、不写文件 |

`/exports` 和 `/exports <ID>` 继续是零模型调用的只读查询，不触发重试。Tk 的再次导出仍通过现有聊天及确认入口，未新增报告管理页面。核对只证明 checked_at 时刻文件一致，后续外部修改仍需重新检查。

首次写文件也补齐了防覆盖窗口：先在同目录写完整临时文件并刷新，再通过硬链接将其排他发布为目标文件；目标即使在最后一次检查之后被其他操作创建，发布也会失败而不会替换原文件。完成后删除临时名字。文件系统若不支持硬链接或没有相应权限，会明确失败并保留待核对记录，不退回“先检查、再覆盖”的写法。常规失败会清理临时文件；强制结束进程时仍可能留下临时文件，本步不提供自动清理或后台续跑。保留单用户本地使用范围，不将文件发布的防覆盖保证扩展为数据库与文件的跨资源原子事务。

用户现在遇到“上次已导出但回复丢失”时，可确认再次导出，直接拿回原结果；自己的文件被修改时会明确收到保护提示。开发者可以区分新写入与复用结果，用原导出 ID 追踪；重复调用不增加记录、不改变文件时间或历史状态，且有可复现的冲突与最终发布竞争测试。此保护只覆盖报告导出，不改变事实/报告保存等其他操作的幂等范围。
