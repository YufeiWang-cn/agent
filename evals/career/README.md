# 求职离线评测与后续模型对照

原有离线脚本入口不读取 `.env`、不调用真实模型。新增独立模型入口，默认只预览，显式执行才加载模型配置；本轮仅用假模型验证。材料全部为合成文本。脚本模型通过真实 Agent 调用业务工具、SQLite 和导出接口，网络客户端使用假的 transport；不能把脚本通过率描述为模型成功率。

## 运行

在仓库根目录、现有 agent 环境运行（源码未安装时设置 `PYTHONPATH=src`）：

```powershell
$env:PYTHONPATH = 'src'
python -m deepseek_agent.evaluation.career_cli --compare-controls --repeat 2 --output data/evals/career-offline.json
```

不改变原有 `eval.py` 通用评测。新入口复用 CheckResult/EvalResult、工作区快照和运行指标收集，单独维护求职多轮协议，避免让单轮代码任务解释新的业务字段。

## 案例与评分

14 个案例共 30 轮，包含：简历+JD 闭环、从零整理、缺信息追问、拒绝事实保存、拒绝报告接受、事实纠正后报告过期、删除事实后初稿过期、个人信息外发、公开查询确认、JD 注入企图、虚构来源引文、工具失败后继续、取消后继续、模型异常后继续。

- 每次案例/重复执行创建独立工作区、会话与档案；同案例的多轮共用真实 Agent 和档案。
- `script` 仅给离线模型动作，`expected` 只给评分器。`$ref: "fact.id"` 从真实工具返回绑定，不预设数据库 ID。被拒绝/失败且不返回对象的动作不能设置 bind。
- `approvals` 按工具与操作设置，默认拒绝，轮次之间不继承。未知操作或字段在加载时拒绝。
- `expected.trace` 检查全部工具顺序及状态；业务断言按 collection/match/count/fields 检查事实版本、报告审阅状态与过期标记。
- 文件检查包含是否存在、必需/禁止文本和意外文件；`network_requests` 是该案例截至当前轮的累计假网络请求数。
- 独立确认检查拒绝“受保护操作成功但没有明确批准”；不是直接调用生产确认策略来给自己判分。
- 终态、工具轨迹、业务状态、文件、隐私和确认分别报告，任一硬检查失败则案例失败。expected 为 failed/cancelled 的负向场景正确终止可以通过。
- 每个失败结果包含具体轮次、检查类别和实际状态；报告保留合成快照和网络 payload，临时工作区随后清理。不要把含真实个人信息的材料直接用于这套会保留观察结果的评测。
- 原指标中的 model_requests/api_attempts 是脚本模型的逻辑调用；token 为估计或不可用，不是账单。`real_api_calls=0` 单独说明真实调用数。

## 离线对照能证明什么

`--compare-controls` 对 01/02 两个闭环案例增加“缺失业务快照”负对照：工具仍正常执行，回答仍然成功，但评分输入中事实/文档/报告被清空。评分器应将两个案例判失败。这只验证评分器不会仅凭成功文案或工具状态放行，不是提示词基线，也不是去掉业务规则后的模型实验。

“缺信息追问”“不夸大职责”等脚本动作是预先指定的，因此离线结果不能证明真实模型会主动追问、抵抗提示注入或忠实改写。伪造引文案例只证明来源约束有效，无法证明引用合法时语义一定正确。未批准写入检测也不能替代完整安全审计。

## 真实模型对照计划：暂不执行

先做 01/02/03/09 四个案例的试点，共 10 个用户轮次。两组分别为同模型的直接提示词回答与完整 Agent 流程，每组每例运行一次：8 次独立任务运行、20 个用户轮次。确认由固定操作策略执行，不额外调用模型生成用户回答。双方使用相同的原始材料、用户补充和评分标准，不把 Agent 私有工具 ID 提供给提示词基线。

独立真实模型入口已接入共享次数预算并关闭自动重试，但真实付费运行尚未执行；两组对照尚待阶段三实现。未来完整试点要求：每用户轮最多 6 次模型请求，整个试点最多 120 次模型请求。输入上限每请求 12000 token、输出上限 2048 token，达到预算停止并记录预算终止，不以缩短/删除失败样例凑分。

保守 token 上限：输入 1440000、输出 245760。设届时核实的每百万输入/输出单价为 P_in/P_out，预算上限为 `1.44×P_in + 0.24576×P_out`；加 20% 预留为 `1.728×P_in + 0.294912×P_out`。不使用当前未知的模型价格冒充实际报价。模型、单价、币种和硬金额上限确定并获得执行授权后才运行。

试点用固定网页快照/假搜索服务消除招聘信息变化与额外搜索费用，只发生模型费用。对比真实联网能力应另开有预算的实验，不能从本试点推断。

输出共同指标：事实忠实度、信息缺口识别、建议可执行性和表达清晰度；分别报告 Agent 的流程完成率、工具操作正确性、安全约束、延迟和 token，不用基线没有的数据库/工具动作要求判基线不合格。试点样本很小，只提供逐例结果，不据此宣称统计显著收益。

## 调用预算接线（已实现，仍只执行离线评测）

离线命令支持 `--max-model-calls N`，同一个批次对象覆盖所有案例、重复运行和负对照。额度用完后后续尝试记录为 `budget_exhausted`，不会再调用模型；这些结果不应解释为模型能力失败。预算中断的负对照不计入 `controls_detected`。不提供此参数时保留离线批次无总额度的原有行为，单轮仍受默认 20 次调用上限约束。报告的 `model_budget` 区分 limit/used/remaining；脚本调用仍为假模型调用，`real_api_calls=0`。

开发者可用 `budget = ModelBudget(120)`，将同一对象通过 `Agent(..., model_budget=budget)` 或 `CareerEvalRunner(model_budget=budget)` 注入多个实例。每轮额度独立重置，批次额度不重置；换一个预算对象或重启进程会创建新额度，因此本实现不支持跨进程/跨重启限额恢复。不能给每个案例分别创建 120 次额度后声称整批总上限为 120。

`RuntimeMetrics` 新增 `budget_rejections` 和 `usage_unknown_attempts`，失败尝试也记录 API usage 或观测估算；usage 缺失的失败不能按零成本处理。调用次数控制在底层模型适配器调用前执行；内置 DeepSeek SDK 重试仍为 0。自定义适配器必须关闭内部重试，否则一次适配器调用可能对应多个供应商请求。

模型入口和估算输入预检已在阶段二接入，默认显式设置 6 次/轮、2048 输出 token。金额预算、人工评分和真实对照尚未实施。


## 模型入口（阶段二，真实付费运行尚未执行）

先预览，默认不读取密钥、不创建客户端、不调用模型，也不写报告：

```powershell
python -m deepseek_agent.evaluation.career_model_cli
```

源码未安装时先设置 `$env:PYTHONPATH = 'src'`。重新安装项目后也可使用 `career-model-eval`。`--manifest` 可选择试点清单，默认 `evals/career/model_pilot.json`；`--repeat` 为 1–10。预览 JSON 展示模型、供应商地址、实际用户任务、确认策略、调用与 token 限制以及源码/案例摘要。

入口只有显式提供 `--execute` 才执行。未来核实模型价格并批准费用后，使用新的 `--output` 路径执行；本轮没有执行该真实分支的网络调用。执行分支读取现有 `.env`，但模型和地址以命令行 `--model`、`--base-url` 为准；默认模型为 `deepseek-v4-pro`、地址为 `https://api.deepseek.com`。无论日常配置如何，评测强制关闭自动重试、使用隔离的求职档案与固定网络快照。

默认只评测完整 Agent 一组：4 个案例、10 个用户轮次，每轮最多 6 次模型调用，整批配置上限 120 次。一次试点实际调用上界是 `min(120, 10×6)=60`；两次重复时上界为 120。与上文未来两组对照的 8 次任务/20 轮不是同一个实验，当前不能输出 A/B 收益。

- `--max-model-calls`：整批共享上限，覆盖所有案例及重复运行；额度耗尽后未开始案例记为 `not_run`，不会创建后续模型。单轮上限由 `--max-calls-per-turn` 设置。
- `--max-input-tokens`：默认 12000，发送前估算完整 messages 和 tools schema，超限不进入供应商适配器；`--max-output-tokens` 默认 2048。输入只是估算，输出限制依赖供应商遵守协议，两者不构成精确金额保证。预检被拒绝仍保守占用一次运行时额度，`provider_attempts` 单独记录真正进入供应商适配器的次数。
- 联网工具始终使用固定合成搜索/网页快照，不使用真实 Tavily 服务。模型服务是未来执行时唯一的联网调用来源；不能据此评价真实招聘信息检索质量。
- 清单复用 01/02/03/09 的原始材料和确认策略，增加明确任务说明。模型仅接收用户任务、正常业务上下文和工具返回；不接收 script、answer、expected 或预设内部 ID。
- 业务评分复用终态、事实/文档/报告、文件、外发及确认检查；不要求真实模型复制离线工具顺序、稳定 key 或报告标题。关键词回答检查不作为语义质量评分。非空回答加正确业务状态仍不代表语义质量达标。

报告逐轮、逐案例以临时文件替换方式更新，不覆盖已有实验报告。保存原始回答、工具轨迹、确认决策、业务快照、预期导出文件正文、预算与用量；因此只使用合成材料，不将真实简历交给这套报告流程。中断时保留已写入的检查点，未开始任务单独列出；本版不自动恢复执行。输入/输出文档、SQLite 和会话存储都在临时目录，案例或重复之间隔离。

`evidence_mode` 区分 `real-model` 和 Python 注入的 `injected-model`。注入模式的 `real_api_calls=null`，不臆测自定义适配器是否联网；本轮测试通过禁止 SDK 和网络、并用 mock 验证真实装配分支，确认实际真实调用为 0。报告的 `human_review` 与 `baseline` 均为 `not_run`，不自动补分或生成对照结论。
